    About

    Where I came from

    I trained in Management Information Systems, then spent a year as a maintenance engineer at Vision Company in Cairo — tracking equipment logs, auditing inventory and sales records, and cleaning up the data-quality problems that were quietly distorting the reports everyone relied on.

    It was not a data role on paper. It is where I found that the interesting problems were in the records, not the machines.

    What I care about

    Systems that can be checked. Anyone can demo a model that works once; the harder question is how you know it still works tomorrow, and how you find out when it doesn't.

    So every project follows the same arc: build it, break it on purpose, then write down what broke. The engineering notes throughout this page are that habit, made public.

    What I offer

    Two tracks that feed each other. Analytics — data modelling, SQL, and dashboards built to answer a specific question rather than display everything at once.

    And applied AI — agentic workflows, retrieval systems with real memory, computer vision, and the evaluation harnesses that keep all of it honest. Whichever side of a problem you start from, I can take it to the other.

    + Engineering note — the guard that saved the pipeline
    IQR capping is standard until a column has zero variance: Q1 and Q3 land on the same value, the fence collapses to a single point, and every row is flagged an outlier at once. The fix was a zero-variance guard that skips capping for those columns rather than trusting the formula blindly. Separately, several columns predicted churn almost perfectly — because they only exist after a customer leaves. Every one of those target-leakage columns was removed before modelling.

    + Engineering note — never assume the fiscal year
    Every time-intelligence measure in DAX inherits whatever year boundary you give it, and the default is January. Before writing a single YTD measure I checked the fiscal calendar in the data itself — it starts in November. Assuming January would have produced measures that ran clean, returned numbers, and were quietly wrong for two months of every year. The broken relationships were the visible bug; this one would never have thrown an error.

    + Engineering note — Groq has no embedding endpoint
    The plan was one provider for everything. Groq serves generation fast and cheaply, but it serves no embedding endpoint at all — and a Qdrant-backed memory is useless without vectors. Embeddings had to come from a second provider, which split the credential and latency story across two services. Related lesson from the same build: never hard-code a Groq model name. They are retired on a schedule, so the model string reads from an environment variable and the deprecation list is something I check, not something I discover in a stack trace.

    4

    agents share one task — and one of them is allowed to reject the other three's work.

    Multi-Agent Deep Researcher

    A Planner breaks the topic into searchable questions, a Researcher runs them through live search, a Writer drafts from that material only, and a Critic judges the result against a rubric.

    The critic → writer edge is the point: it turns a pipeline into a loop. In a typical run the Critic rejects the first draft and the second comes back with the structure and real citations it asked for.

    LANGGRAPHGROQSERPAPIREDIS STACK
    REPOSITORY →
    + Engineering note — malformed tool calls you can't reproduce
    Llama through Groq intermittently emits tool calls that don't parse. The failure is non-deterministic — the same prompt succeeds on the next run, so switching model doesn't fix it and neither does a better prompt. What works is an escalation ladder: retry once with the parser error fed back as a correction, then force the tool with tool_choice, then fall back to a tool-free answer rather than crashing the graph. Reasoning models add their own twist — a <think> block before the answer and JSON fenced anywhere in the reply — so every response goes through one shared defensive parser instead of five hopeful ones.

    Multimodal Vision OCR Agent

    Three OpenCV stages run first: deskew without clipping the corners, a CLAHE contrast lift tile by tile, and a rescale onto the 28px patch grid the vision transformer expects.

    Only then does Qwen vision read it through the Groq API, returning structured JSON rather than loose text — nine fields from a scanned repair invoice in about four seconds.

    OPENCVQWEN VISIONGROQFASTAPISTREAMLIT
    REPOSITORY →
    + Engineering note — rotation that eats the corners
    Rotating an image in place keeps the canvas the same size, so the corners of a 9.5°-skewed page rotate straight out of frame — and the part that disappears first is usually the header with the invoice number on it. Deskew therefore runs on an expanded canvas sized to the rotated bounding box. The resize is not arbitrary either: the vision transformer reads the page in 28-pixel patches, so any dimension off that grid gets silently padded before inference. Aligning to it first keeps what the model sees identical to what I processed.
